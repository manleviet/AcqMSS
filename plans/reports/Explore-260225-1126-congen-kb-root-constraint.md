## 1. ConGen KB Output: What Constraints Are Included?

### 1.1 KB Production Pipeline

ConGen produces `kb_constraints` through a three-stage pipeline:

```
E+ (positive examples) + E- (negative examples) + Bias (B) + Background (BG)
    ↓
    GenerateNE: E- → NE (negated negative examples)
    ↓
    AcqMSS: Find Maximum Satisfiable Subset of B
    ↓
    REDUCE: Remove redundant constraints
    ↓
    ConGenResult with kb_assumption_ids
    ↓
    Mapped back to constraint names (via DescriptionProvider)
    ↓
    kb_constraints: List[str] (constraint names/IDs)
```

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/algorithms/acqmss/congen.py:140-154`

### 1.2 KB Constraint Types

The final KB contains TWO types of constraints:

1. **Bias Constraints (B')**: Constraints from the original bias that survive the MSS finding
   - Non-redundant subset of the input bias B
   - Must remain consistent with positive examples
   - Must help reject negative examples

2. **Negated Examples (NE)**: Blocking clauses derived from negative examples
   - Generated by GenerateNE from E-
   - Each NE is a minimal conflict set derived via QuickXPlain
   - Format: NOT(assignment1 & assignment2 & ...) 

**Code References**:
- `REDUCE Algorithm` (conacq/algorithms/acqmss/reduce.py:27-34): `KB ← B' ∪ NE`
- `ConGen.acquire()` (conacq/algorithms/acqmss/congen.py:128-136): Returns `kb = B' ∪ NE`

### 1.3 Constraint Description Mapping

In `ConGenRunner.run()` (conacq/runners/congen_runner.py:244-250):

```python
# Map assumption IDs back to constraint names
for aid in result.kb_assumption_ids:
    cname = provider.get_description(aid)
    kb_names.append(cname)
    if cname in self.model.constraint_map:
        kb_clauses.extend(self.model.constraint_map[cname])
```

The DescriptionProvider tracks:
- **Bias constraints**: Original constraint IDs (e.g., "c1", "c2", "id → db")
- **NE constraints**: "NOT(feature1=true & feature2=false & ...)"
- Names stored during task preparation (ConGenTaskPreparation)

### 1.4 Root Constraint Inclusion/Exclusion

**THE ROOT CONSTRAINT IS EXCLUDED FROM kb_constraints**

Evidence:
1. **Root in Background Knowledge (BG)**: Root constraint belongs to `set_bg` (background), not `set_b` (bias)
   - File: conacq/algorithms/acqmss/task_preparation.py:88-95
   - `bg_data.set_kb` and `bg_data.assumptions` extracted from Oracle

2. **ConGen Input Separation**: 
   - `set_b` = Bias constraints (only these can enter KB)
   - `set_bg` = Background knowledge (stays in background, not acquired)
   - File: conacq/algorithms/acqmss/congen.py:65-88

3. **REDUCE Does Not Include BG in Result**:
   - Algorithm: `KB ← B' ∪ NE` (neither contains BG)
   - Root already in BG, so never added to KB
   - File: conacq/algorithms/acqmss/reduce.py:62-63

4. **KB Comparator Excludes BG**:
   - Description-based: Only maps bias constraints (skips NE with "ne_" prefix)
   - Clause-based: Adds BG clauses separately: `if result.bg_clauses: ... kb_clauses.add(...)`
   - File: conacq/eval/kb_comparator.py:107-162

## 2. Root Constraint: Definition and Location

### 2.1 What Is the Root Constraint?

**Definition**: The "root constraint" is the **mandatory feature** constraint that enforces the root feature must always be selected.

**Form**: `[root_feature_var]` (unit clause)

**Example** (REAL-FM-7):
- Feature model root: "REAL_FM_7"
- Constraint: `REAL_FM_7 must be selected` 
- CNF: `[var_id]` where `var_id` is SAT variable for REAL_FM_7

### 2.2 Root Constraint In Code

#### 2.2.1 FM Transformation (Source of Root)

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/explanation/transformations/fm_to_diag_pysat.py:36-42`

```python
def add_root(self, feature: Feature) -> None:
    var = self.destination_model.variables.get(feature.name)
    if var is None:
        raise KeyError(f'Feature {feature.name} not found in the model')
    
    self.destination_model.add_clause([var])
    self.destination_model.add_clause_to_map(str(feature), [[var]])
```

The root feature is converted to a unit clause `[var]` and stored as the **first constraint** in the constraint_map.

#### 2.2.2 Oracle Model Assumption Layout

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/oracle/fm_oracle_model.py:191-201`

```
Shared Assumption ID Layout (Oracle owns Parts 1-4):
  Part 1: Feature variable IDs (1..n)               [FmToPysat]
  Part 2: Tseitin vars (negated FM constraints)     [FmToPysat]
  Part 3: FM constraint assumptions (paired)        [This method]
```

The root constraint gets the **first pair of assumption IDs**: `(assumption_id_0, assumption_id_1)`

## 3. Ground Truth KB Construction

### 3.1 GroundTruthData Structure

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/oracle/ground_truth.py:14-63`

```python
@dataclass
class GroundTruthData:
    descriptions: Set[str]              # Set of constraint descriptions
    clauses: List[List[int]]            # All CNF clauses
    clause_set: Set[Tuple[int, ...]]    # Normalized (sorted) clause tuples
    feature_map: Dict[str, int]         # Feature name → variable ID
    root_feature: str                   # Name of root feature
```

Created from FM via:
```python
@classmethod
def from_uvl(cls, uvl_path: Path) -> 'GroundTruthData':
    fm = UVLReader(str(uvl_path)).transform()
    fm_model = FmToDiagPysat(fm, create_negation=False).transform()
    
    descriptions = extract_constraint_descriptions(fm)  # From FM hierarchy + CTCs
    clauses = [clause for clauses in fm_model.constraint_map.values()
               for clause in clauses]
    clause_set = {tuple(sorted(c)) for c in clauses}
    feature_map = dict(fm_model.variables)
    root_feature = fm.root.name
    
    return cls(descriptions=descriptions, clauses=clauses, 
               clause_set=clause_set, feature_map=feature_map, 
               root_feature=root_feature)
```

### 3.2 Does GroundTruthData Include Root Constraint?

**YES** ✓

The ground truth includes ALL FM constraints, including the root:

1. **Root clause included**: `clauses` = all constraint_map clauses → includes root unit clause `[root_var]`
2. **Root description included**: `descriptions` = extract_constraint_descriptions(fm) → includes feature relationships/CTCs, and implicitly root via feature name
3. **Root in clause_set**: `clause_set` includes root as `(root_var_id,)` tuple

**Code Path**:
1. FmToDiagPysat.transform() calls add_root() → adds `[root_var]` to constraint_map as first constraint
2. GroundTruthData.from_uvl() reads constraint_map → all clauses (including root)
3. Descriptions extracted from FM features/relations → includes all relationships including root

## 4. KB Comparison & Evaluation Metrics

### 4.1 KBComparator Strategies

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/eval/kb_comparator.py`

Two comparison strategies:

#### Strategy 1: Description-Based (RECOMMENDED)

**Method**: `_compare_by_description()` (lines 107-162)

```python
# Get FM descriptions from oracle
fm_descriptions = self.oracle.descriptions  # Set of strings

# Get KB descriptions from bias
for cid in result.kb_constraints:
    if cid.startswith('ne_'):
        continue  # Skip NE constraints
    if self.bias.has_constraint(cid):
        desc = self.bias.get_description(cid)
        acquired_descriptions.add(desc)

# Compare string sets
tp = acquired_descriptions & fm_descriptions
fp = acquired_descriptions - fm_descriptions
fn = fm_descriptions - acquired_descriptions
```

**Key Characteristics**:
- Compares natural language descriptions (strings)
- **Excludes NE constraints** (lines 122-123)
- **Only includes bias constraints** (lines 124-127)
- Assumes oracle descriptions match bias descriptions

#### Strategy 2: Clause-Based (SEMANTIC)

**Method**: `_compare_by_clause()` (lines 164-218)

```python
# Convert KB constraint IDs to normalized clause sets
for cid in result.kb_constraints:
    if cid.startswith('ne_'):
        continue  # Skip NE constraints
    if self.bias.has_constraint(cid):
        for clause in self.bias.get_clauses(cid):
            normalized = tuple(sorted(clause))
            kb_clauses.add(normalized)

# Union background clauses (KB ∪ BG)
if result.bg_clauses:
    for clause in result.bg_clauses:
        normalized = tuple(sorted(clause))
        kb_clauses.add(normalized)

# Compare clause sets with oracle
metrics = compute_metrics(kb_clauses, self.oracle.clause_set, bias_clauses)
```

**Key Characteristics**:
- Compares CNF clauses semantically (as integers)
- **Excludes NE constraints** (lines 175-176)
- **Includes BG clauses** (lines 186-189)
- BG clauses merged into KB for comparison: `KB ∪ BG`

### 4.2 Metrics Calculated

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/eval/metrics.py`

```python
TP = matched constraints (in both KB and oracle)
FP = extra constraints (in KB but not oracle)
FN = missed constraints (in oracle but not KB)
TN = not applicable (set-based comparison)

Accuracy  = (TP + TN) / (TP + TN + FP + FN)   [But TN=0, so not used]
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 * P * R / (P + R)
```

### 4.3 Root Constraint Treatment in Evaluation

**NOT compared directly because**:

1. **Description-based**: Root never matches (constraint in oracle, not in bias)
2. **Clause-based**: Root in BG, not acquired separately
   - Root clause added to oracle.clause_set automatically
   - Root clause in result.bg_clauses (if present)
   - Merged into KB for comparison, so semantically "compared" but not counted as acquisition

**Implication**: Metrics measure acquisition of bias constraints only, not root constraint.

## 5. Background Knowledge (B) Handling in ConGen

### 5.1 Is Root Constraint Part of Background Knowledge?

**YES** ✓

The root constraint is **exclusively** part of background knowledge:

**File**: `/Users/manleviet/Development/GitHub/AcqMSS/conacq/algorithms/acqmss/task_preparation.py:88-95`

```python
# Step 0: Copy BG data from Oracle (root constraint pair from Part 3)
bg_data = oracle.get_bg_data()
result.set_kb.extend(bg_data.set_kb)           # Root clauses added
result.assumptions.extend(list(bg_data.assumptions))
result.negation_map.update(bg_data.negation_map)
```

Root is copied into `set_kb` via BGData → becomes part of the solver knowledge base.

### 5.2 Root During ConGen Execution

**Step 1: Initialization**
- Root copied to task.set_kb (always active in solver)
- `set_bg = [root_assumption_id]` passed to ConGen.acquire()

**Step 2: Consistency Check**
- ConGen.acquire() (lines 96-100):
  ```python
  inconsistent = self.checker.is_consistent_test_cases(
      set_neg_tv + set_bg,  # NE ∪ BG  ← Root here
      set_tc,               # E+
      stop_at_first_violation=True
  )
  ```
  Root in BG ensures positive examples respect feature model hierarchy.

**Step 3: AcqMSS Finding**
- AcqMSS receives `set_bg` with root
- Root never removed (not in bias B to be minimized)
- Stays constant throughout algorithm

**Step 4: REDUCE**
- REDUCE receives `set_bg` with root
- Root not tested for redundancy (only KB constraints tested)
- Remains in final result

**Step 5: KB Output**
- Root NOT in `result.kb_assumption_ids`
- Root in `result.bg_clauses` (line 138: `[[lit] for lit in set_bg]`)
- KB output is bias + NE only

## 6. Summary: KB Constraints Composition

### What IS in kb_constraints?

1. **Bias Constraints**: Non-redundant subset of input bias B
   - Must be consistent with E+
   - Must help explain E-
   - Learned via AcqMSS → REDUCE pipeline

2. **Negated Examples (NE)**: Blocking clauses from E-
   - Generated by GenerateNE
   - Each NE = minimal conflict from QuickXPlain
   - Added to KB to explicitly reject negative examples

### What is NOT in kb_constraints?

1. **Root Constraint** ✗
   - Stays in background knowledge (BG)
   - Never acquired or learned
   - Essential FM constraint (always true)

2. **Other FM Constraints** ✗
   - Not in bias → not candidate for acquisition
   - May be implicitly used via BG during checks

3. **Feature Variable Assignments** ✗
   - Support clauses for testing
   - Not part of constraint KB
